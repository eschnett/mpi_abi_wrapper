  What still answers MPI_ERR_UNSUPPORTED_OPERATION is decided per
  build by dev/probe_impl.py: an entry point the implementation does
  not declare, hand-written or generated alike (decision 6).

  One limitation is this library's rather than the implementation's,
  and belongs here because no probe reports it: where the
  implementation has no MPI_BUFFER_AUTOMATIC (it is MPI-4.1), the
  wrapper emulates it with a fixed buffer of its own
  (MPIWRAPPER_AUTOBUF_BYTES, 8 MiB). The standard's 'buffer of
  sufficient size' is unbounded, so a program that would have run
  against a real automatic buffer can still see MPI_ERR_BUFFER.

Implemented on the ABI side (5)
----------------------------------------
  The entry points MPI-3.0 deleted from the standard. The ABI header
  still declares them, because an ABI is a promise about symbols -- but
  an implementation need not define them any more, and Open MPI main's
  libmpi_abi does not. Forwarding through a slot would make that a
  *link* failure of the whole wrapper rather than the run-time report
  decision 6 promises, because the probe asks the compiler and the
  compiler sees the declaration.

  So libmpi_abi answers these itself, by calling the slot of the entry
  point that replaced each. They have no slot and no wrapper body, and
  they now work over any implementation with the MPI-2 attribute
  interface rather than only over one that kept the MPI-1 spelling.
  The generator checks each pair's return type, arity and parameter
  types, so a signature that drifts fails generation.

    MPI_Attr_delete -> MPI_Comm_delete_attr
    MPI_Attr_get -> MPI_Comm_get_attr
    MPI_Attr_put -> MPI_Comm_set_attr
    MPI_Keyval_create -> MPI_Comm_create_keyval
    MPI_Keyval_free -> MPI_Comm_free_keyval

Staged past return (8)
----------------------------------------
  These convert an in-direction array *and* hand back a request, so the
  implementation may still be reading the temporary after the call
  returns: the block is owned by the request and freed when the
  implementation nulls the handle -- at completion for a nonblocking
  operation, at MPI_Request_free for a persistent one (NOTES.md #5.7).
  This is the one property no assertion here can check, which is why
  the set is a frozen tally and why test/abi_arrays_test.c exercises
  both lifetimes.

    MPI_Alltoallw_init_c
    MPI_Ialltoallw
    MPI_Ialltoallw_c
    MPI_Ineighbor_alltoallw
    MPI_Ineighbor_alltoallw_c
    MPI_Neighbor_alltoallw_init

Deferred to S3 (0)
----------------------------------------
  None: S3 is complete, and every one of the entry points above is
  either generated or named in the ledger. The section stays, and
  so does its frozen tally of zero, because that is what makes a
  future apis.json or ABI header introducing an argument class the
  generator cannot place fail here -- rather than quietly emitting
  one more run-time-reporting stub.

Returns MPI_ERR_UNSUPPORTED_OPERATION at run time
----------------------------------------
  ...for every entry point above that is deferred or hand-written
  without a body yet, and -- per implementation, decided by
  dev/probe_impl.py at configure time -- for every generated one
  the implementation does not define. The second set is a property of
  the build, not of the generator, so it is not listed here.
