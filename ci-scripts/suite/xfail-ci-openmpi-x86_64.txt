# Four runs:
#
#     32182485327   x86_64 failed                      -> listed here

# **aarch64 fails it every time; x86_64 fails it some of the time.** Both earlier
# readings were single-run inferences, and the second one was made in this file while
# quoting the warning against exactly that.
#
# What reconciles them is the mechanism, which is new: it *segfaults*, in
# MPI_T_pvar_get_info through this project's wrapper and into Open MPI's
# mca_base_pvar_get -- "address not mapped", at 0x44 -- alongside 599 errors from the
# `strlen(desc) + 1 == min(desc_len, STR_SZ)` check that NOTES.md #5.8 makes ours. A
# bad pointer lands on a mapped address sometimes and not others, so one bug that is
# always present explains a reliable symptom on one architecture and an intermittent
# one on the other. There is no need for two explanations.
#
# It is listed nowhere, and cannot be: it flaps on x86_64, so listing it fails the
# runs it passes. That is also the wrong remedy -- a segfault through our own code is
# a bug to fix, not an expectation to record.
#
# **One cause was found and fixed; whether it was the whole cause is not yet known.**
# decision 6's stub used to leave non-handle out parameters untouched, and this test
# does `int num_sources; MPI_T_source_get_num(&num_sources); for (i = 0; i <
# num_sources; i++)` over an Open MPI that has no MPI_T_source_get_num -- so the loop
# bound was stack garbage, which is exactly the shape of a symptom that is reliable on
# one architecture and intermittent on the other. NOTES.md decision 6 now requires a
# stub to define every `out` scalar, and it does.
#
# What that does *not* explain is the faulting call itself. The backtrace crashes in
# MPI_T_pvar_get_info, which Open MPI does have, so it is not a stub; and its two call
# sites in this test take their index from MPI_T_pvar_get_num and from
# MPI_T_category_get_pvars, both also present and both faithful passthroughs here.
# Open MPI's own bounds check is worth knowing about while chasing the rest:
# mca_base_pvar_get_internal tests `index >= pvar_count` and *not* `index < 0`, its
# `assert(*pvar)` is compiled out in the -O3 -DNDEBUG build install-openmpi.sh
# produces, and opal_pointer_array_get_item omits the negative check too -- so a
# negative index is an unchecked wild read rather than MPI_T_ERR_INVALID_INDEX. The
# fault address 0x44 is exactly offsetof(mca_base_pvar_t, flags) on LP64, which is
# `(*pvar)->flags` with *pvar NULL. The next run of this shard is the experiment:
# if mpit_vars still fails, the remaining index source is what to find.
#
# **One of these three is the hypothesis this project has been carrying, now
# reproduced on a second Open MPI release.** `coll/allred 4` gets wrong answers for
# MPI_SUM over MPI_UNSIGNED_CHAR, MPI_INT8_T and MPI_UINT8_T -- the 8-bit integer
# types and no others -- on x86_64 and not on aarch64. The same failure appeared
# over Open MPI 4.1.6 on x86_64 and not on the aarch64 run that produced the older
# list. Open MPI's AVX reduction component is x86-only, which fits two versions,
# one architecture and one family of types better than anything on our side does.
# `OMPI_MCA_op=^avx` is the one-variable check nobody has run yet, and building the
# test with Open MPI's own mpicc is what would settle it.
#
