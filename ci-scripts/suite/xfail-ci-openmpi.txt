# check-tap.py enforces it in both directions -- an unlisted failure fails the

# with no reason after the colon fails the run too.

# **Written from run 32182485327**, the first run in which an Open MPI leg got far
# enough to produce results: three of its four shards completed and the fourth did
# not (see "rma" below). Per shard, on aarch64: coll 192 tests / 8 failed, p2p 137
# / 20, rest 316 / 82. That run put 109 lines here, the failures both architectures
# produced, and four in the two delta files. **There are 105 now**

# it moved here from the x86_64 file, which explains its own longer reason below.

# so the next reader does not have to trust this one either.
#
# **`rma` is missing from this list, and it is no longer a gap: the directory is not
# run on the Open MPI legs.** It was a gap for a while -- both shards were killed six
# minutes in with "the runner has received a shutdown signal", on both architectures,
# twice each -- and teeing runtests into the job log localised it, first to
# `./rma/testlist.dtp [176 tests]` and then, once the monitor was added, to individual
# tests. The cause turned out to be upstream and not a triage problem.
#
# Open MPI 5.0 removed the `osc/pt2pt` one-sided component. `osc/rdma`, which replaces
# it, appears to build per-element state for a derived datatype where pt2pt packed and
# streamed it, so the cost tracks a datatype's *element count* rather than its byte
# count. `rma/transpose1` -- 3.8 MB of payload, `MPI_Put` onto a million discontiguous
# elements -- takes at least 14.6 GB and a 16 GB runner with it, where Open MPI 4.1.8
# completes the same test with the same wrapper in 1.7 GB. Neither `--mca btl self,sm`,
# nor a libfabric build with a real accelerated `btl/ofi`, nor excluding the offending
# test lines reaches it; the last only moves the death to the next casualty, because
# the casualties are chosen by datatype shape and no testlist line shows that.
#
# So `.github/workflows/ci.yaml`'s suite matrix excludes `rma` on these two legs, and
# there is nothing for this file to expect. `errors/rma/*` still runs, because the
# shards split on top-level directories, and its lines are below. Re-adding the shard
# is a two-line revert if an Open MPI release restores a streaming one-sided path.
#
# ci-scripts/suite/README.md has the rest, including the run ids for every
# measurement above.
#
# **Excluding rma does not by itself make these legs gate, and they stay
# report-only.** One thing is still outstanding and it is not rma: `openmpi /

# the next. Open MPI has a shard that hangs intermittently as well as the one that
# died reproducibly, and a green Open MPI leg needs that settled too.
#

# reaches, so the surface is there and what differs is behaviour.
#

# wrong *data* -- "expect 0, got 255" -- and 255 is not data at all but the exit

# **The four threads/pt2pt/mt_*probe* lines below are a family, they are Open MPI's,
# and the family flaps.**
#
# **Attributed, finally, and not to us.** Run 32418464622 built the same suite tree
# twice against the same Open MPI 5.0.10 -- once through this project's prefix and once
# against Open MPI directly -- and ran all four in each. With **no wrapper in the path
# at all**, eight of eight native runs failed: seven printed the same
# `MPI_ERR_COUNT: invalid count argument` out of MPI_Recv that the wrapped leg shows,
# and the eighth aborted identically with the message past the captured tail. The
# wrapped leg in the same run reproduced as listed -- 61 tests, 11 failures, 11 expected
# and 0 unexpected. So this is an Open MPI bug reachable without this project, which is
# what two releases of "not yet attributed" could not say because the tests had only
# ever been run through the wrapper.
#
# For whoever takes it upstream, the path is short and the arithmetic is not in doubt:
#
#     int recv_count = -1;
#     MPI_Iprobe(...);  MPI_Get_count(status, MPI_INT, &recv_count);
#     MPI_Recv(buff, recv_count, MPI_INT, ...);          /* MPI_ERR_COUNT */
#
# so the count reaching MPI_Recv is negative -- either still -1, because MPI leaves an
# out parameter alone on an error return, or MPI_UNDEFINED, which Open MPI's
# MPI_Get_count returns when the status byte count is not a multiple of the datatype
# size. Both are legitimate, so the question is why the probe's status carries a
# _ucount that is not a whole number of MPI_INTs under MPI_THREAD_MULTIPLE. ob1's
# iprobe copies the whole status including _ucount on a match and leaves it untouched
# on a miss, which is where reading ran out and measuring took over.
#
# **And the family still flaps, which is separate from whose bug it is.** *Which* member
# trips in a given run moves with thread timing. Run 32409072194 is the demonstration:
# mt_iprobe_isendrecv failed (as listed) while mt_iprobe_sendrecv passed, and the gate
# went red on "EXPECTED FAILURE THAT PASSED" with zero unexpected failures.
#
# check-tap.py has no way to express that. It is strictly bidirectional -- an unlisted
# failure, a listed test that passed, and a listed test that did not run all fail the
# run -- so for a test that flaps, listing it fails the runs it passes and not listing
# it fails the runs it fails. There is no placement of these four that is stable, and
# moving them between this file and the per-architecture ones only moves which run goes
# red. They are left listed because they fail far more often than they pass; the p2p
# legs are report-only, so the cost is noise rather than a blocked merge.
#
# Fixing it properly means either attributing the underlying MPI_ERR_COUNT bug, or
# giving check-tap.py a way to say "may fail or pass" -- which is a change to what the
# gate means and wants deciding on its own, not in passing.
