# Expected failures of MPICH's C test suite over this project in GitHub Actions,
# over MPICH 5.0.1 on **i386 only**. This is the delta beside
# xfail-ci-mpich.txt, which holds what every architecture sees; check-tap.py
# reads the two as one and rejects a test listed in both.
#
# 32-bit x86, in the linux/386 container ci-scripts/suite/i386-suite.sh drives.
# This is the only row where an ABI handle is 4 bytes rather than 8 (NOTES.md
# #4.1), so it is where a scheme relying on spare high bits would break and where
# #4.2's status layouts are at their tightest. Failures unique to ILP32 -- large
# counts that no longer fit, a datatype extent that overflows, anything about
# sizeof -- belong here rather than in the shared list.
#
# **All four shards of this row now finish, and the reason they did not was one
# missing Docker flag.** This is the only suite row that runs inside `docker run`,
# so it was the only one whose /dev/shm was Docker's default 64 MB against the
# runner's own 7.9 GB -- and MPICH leaks its shared segments into that tmpfs, 24
# files and 39 MB left behind by 283 tests, none reclaimed. Once it fills, every
# further MPI_Init-era mapping raises SIGBUS. That is what the `rest` shard's ~140
# extra failures were, and why it never finished: 172 failures and 139 SIGBUS,
# against x86_64's 33 for the same shard.
#
# ci-scripts/run-linux-docker.sh now passes --shm-size, and in run 32434698299
# `rest` went green in **3 minutes 38 seconds** with x86_64's numbers exactly --
# 316 tests, 279 passed, 33 failed, 4 skipped, nothing unlisted, no SIGBUS -- where
# every attempt before it died at 49-52 minutes with no result at all.
# ci-scripts/suite/README.md's "The i386 `rest` shard" has the two-leg measurement
# and what it does not settle.
#
# **So this file is a delta of six lines rather than eleven.** Five retired in that
# run because they were the tmpfs rather than the architecture, and the gate is
# what named them -- `EXPECTED FAILURE THAT PASSED`, which is the rule that a list
# cannot quietly keep a line that has stopped being true:
#
#     coll/bcast 4, coll/bcast_comm_world_only 10, coll/bcasttest 16, coll/bcasttest 32
#     coll/reduce 10
#
# The four bcast lines were the ones asking 4 to 32 ranks' worth of shared memory
# of a 64 MB tmpfs, and their `EXIT CODE: 9` was a rank being killed rather than a
# collective being wrong. coll/reduce 10 is the timing knife-edge
# ci-scripts/suite/README.md measures at 179.7 s of a 180 s limit, and this row is
# the one MPICH leg that had been running without the MPITEST_TIMEOUT_MULTIPLIER: 2
# the others set; it now has it, which is the cause rather than the symptom. If it
# flaps again, flaky-ci-mpich.txt is where it goes.
#
# **All 41 lines of xfail-ci-mpich.txt hold here unchanged**, across all four
# shards, with nothing in it failing to fire -- so ILP32 adds to that list without
# contradicting it, which is what the shared/delta split is for. The six lines
# below are the additions.
#
# **They are two shapes, and both survive a /dev/shm with room in it**, which is
# the one thing run 32434698299 added to their attribution: whatever they are, they
# are not the container.
#
#     typerep_yaksa_pack.c line 326: element_size < 0     (coll/redscatbkinter, coll/gather)
#     internal_Send_c: Invalid buffer pointer             (pt2pt/pt2pt_large)
#     ch4_impl.h line 850: map_entry != NULL              (rma/win_large_shm)
#
# A negative element size and a rejected buffer pointer, in datatype packing and in
# the large-count send, on the one architecture where an ABI handle is 4 bytes and
# MPI_Aint is 4 bytes while the ABI's MPI_Count is 8. NOTES.md #4.1 and #4.2 say
# 32-bit is where those assumptions bite, and a truncation or a sign extension
# across that boundary would look exactly like this. **It may well be ours.** Every
# one of these tests passes on x86_64 and aarch64 with the same wrapper build and
# the same MPICH 5.0.1, so the difference is the architecture and not the release.
# What settles it is the method S7 used throughout, and which the shm probe has now
# made routine: build coll/gather and pt2pt/pt2pt_large with MPICH's own mpicc
# inside the same linux/386 container and see whether the assertion still fires with
# no wrapper in the picture. `ci-scripts/suite/i386-shm-probe.sh` does exactly that
# for two named tests and takes them from MPIABI_PROBE_TESTS, so it is a matter of
# pointing it here. Until that is done these lines say what was seen and claim
# nothing about whose bug it is.
#
# rma/win_large_shm is likelier to be honest, and the shm run is evidence for that
# reading rather than against it: a 32-bit process has 4 GB of address space and the
# test asks for a large shared window, so 8 GB of /dev/shm cannot help it and did
# not. MPICH asserting rather than returning an error is its own choice about an
# impossible request.
#
# One line per test, `<dir>/<program> <np> : why`, in runtests' own naming.
# check-tap.py enforces it in both directions -- an unlisted failure fails the
# run, and so does a listed test that passed or that did not run -- and a line
# with no reason after the colon fails the run too. `--update-xfail` writes bare
# lines for a human to add reasons to; it can never make a red run green.
#
# **CI's lists are separate from the local ones on purpose.** xfail-mpich.txt and
# xfail-openmpi.txt describe one development laptop, and three runs established
# that the two environments genuinely disagree: on a four-vCPU runner every test
# asking for more ranks than there are cores runs 5-7x slower, while everything
# at four ranks or fewer runs 5-25x *faster*, so timing expectations move in both
# directions at once. One file cannot be true of both machines.
#
# **This list is no longer empty and no longer a placeholder**, which is the whole
# difference run 32434698299 made: it says what ILP32 adds over the shared list,
# measured on four shards that all finished, rather than saying nothing has been
# triaged. The row gates.
